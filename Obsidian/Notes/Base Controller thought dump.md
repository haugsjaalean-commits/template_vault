There would only ever be one base that simply changes itself to adapt to the context and inputs of the user. This base would be controlled by something called the `Base Controller`. The base controller would be a wrap around the base. The Base Controller would have a list of queries. Queries will often have the option to input a value. They will often also have the option for this value to be the active file or something property of the active file. Views will also all be interchangeable, and they will no longer contain any information about the query. Each view will simply give information about how to display the file. 

## New ideas


Each base controller would be attached to a base. Each base controller would also communicate with two other panels: the view panel and the query panel. Each base controller is simply a list of active queries and one selected view. There are no individual views in each base controller view. In fact, that feature isn't used. The base controller communicates with the base underneath only with the global queries and one main view. In the queries menu in each base controller, there can be special menues for manipulating queries. One of these menues would be for managing class related queries. It would be exactly like the one that is currently implemented in the class base menu. 


### Slightly changed idea 

I said that base controllers wouldn't allow for the creation of individual views inside of the bases, but I think that this was an overstep. I have two ideas currently: either implement multiple views in the base controllers, or achieve a similar behavior thanks to grouped queries. If I implement advanced options for manipulating queries with astounding speed, then having views would be useless. This does raise one question, however: is the point of making hyper flexible bases so that users can easily create (and keep up to date) new bases without having to copy work, or is the point to allow people to easily and flexibly make changes to queries on the fly? The answer is that base controllers solve both problems. So why not use it for both? 





### Advanced features

Specific views could be linked to a certain set of queries that will be applied automatically whenever that view is turned on. This could notably be useful for turning on the graph view. There are certain types of notes that will simply clutter up a graph view, so it will be helpful to automatically filter them out whenever the graph is turned on. Of course, the user can turn them off if they don't want them, but, as long as they leave them on more than they turn them off it is a worthwhile exchange.
